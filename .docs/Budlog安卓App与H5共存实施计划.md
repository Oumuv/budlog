# Budlog 安卓 App 与 H5 共存实施计划

## 1. 计划摘要

Budlog 保留现有 H5 作为唯一的业务页面实现，新增一个独立的 Android 薄壳应用，通过 App WebView 加载同一套线上 H5。

```text
桌面/手机浏览器 ──────────┐
                              ├─ HTTPS H5 ── /api/v1 ── Budlog Server
Android App ── 原生薄壳 ── WebView ─┘
```

本方案的目标是：

- 浏览器继续使用现有 H5，不拆分两套业务页面。
- H5 页面、样式和普通业务逻辑调整通过服务器发布生效，不重新安装 APK。
- APK 只承担 WebView 容器、启动、网络错误、安全边界和少量必要的原生能力。
- 后续需要可靠的后台提醒或锁屏白噪音时，通过受控原生桥接扩展，不将任意原生 API 暴露给远程页面。

本计划中“H5 在线发布”是指更新服务器上的 Web 资源，不是修改已安装 APK 内的原生代码。

## 2. 实施边界

### 2.1 首期范围

- 新增 Android 薄壳，加载固定 HTTPS H5 地址。
- 保留现有 H5 构建、PWA 和浏览器访问方式。
- 区分普通浏览器与 Android App 内嵌环境。
- 建立 H5 版本检查、刷新提示、发布和回滚机制。
- 处理 Android 返回键、断网、加载失败、外部链接和安全域名边界。
- 完成桌面 H5、`390x844` H5 和 Android 真机三类验收。

### 2.2 首期不包含

- 不将现有全部页面编译为本地 `app-plus` 页面。
- 不在首期接入任意 JavaScript 到原生代码的通用桥接。
- 不以 WGT 作为 H5 页面的主发布手段。
- 不承诺首期支持断网业务操作、后台定时提醒或锁屏持续播放。
- 不在未确定发行渠道前进行应用商店上架配置。

## 3. 当前架构与兼容性基线

### 3.1 可直接复用的部分

- `budlog-app` 是 Vue 3 + TypeScript + uni-app H5，现有业务页面可作为 WebView 中的普通网页运行。
- `budlog-app/src/api/request.ts` 默认使用同源 `/api/v1`；App 加载正式 H5 域名时，可继续由 Nginx 反向代理 API，无需改为跨域请求。
- 家庭密码继续由 H5 通过 `X-App-Password` 请求头传递，不需要传给 Android 壳层。
- Nginx 通过 `deploy/h5/` 绑定挂载提供 H5，更新该目录后 Web 容器可直接读取新产物。
- Vite 生成的主要 JS/CSS 资源使用带哈希文件名，适合长时间缓存。

### 3.2 需要改造或隔离的部分

- `budlog-app/package.json` 只有 H5 开发、H5 构建和类型检查脚本，没有 App 编译依赖。
- `budlog-app/src/manifest.json` 的 `appid` 为空，且 Android 权限列表存在多项与当前业务无关的高权限，不应直接用于发布 APK。
- H5 启动时会初始化 PWA 并注册 Service Worker；App 内嵌环境不需要再展示“添加到桌面”。
- `public/sw.js` 对导航请求使用网络优先，但当前没有独立的 H5 `buildId`、版本检查或用户可见的刷新机制。
- `deploy/nginx.conf` 已对 `sw.js` 设置 `no-cache`，但没有为 `index.html` 和版本清单建立明确的禁止强缓存策略。
- 提醒当前仅在应用前台每 60 秒轮询，`App.vue` 在隐藏时会停止轮询，WebView 壳不会自动把它变成后台提醒。
- 白噪音使用 `HTMLAudioElement` 和 Media Session，前台可继续使用，但 Android 后台、锁屏和系统回收场景不能作为可靠验收项。
- Naive UI、DOM/PWA API 和浏览器音频 API 在现有页面中已被广泛使用；将全部页面直接编译为 `app-plus` 的改造面和回归风险明显高于 WebView 薄壳。

### 3.3 兼容性预期

| 能力 | 浏览器 H5 | Android WebView 薄壳 | 说明 |
| --- | --- | --- | --- |
| 宝宝、喂养、尿便、任务、时间线等 CRUD | 保持 | 预期兼容 | 使用同一 H5 和同源 API |
| 家庭密码记住 | 保持 | 独立保存 | WebView 存储与 Chrome 不共享 |
| PWA 安装 | 保持 | 隐藏 | App 内不再引导二次安装 |
| 应用内前台提醒 | 保持 | 预期兼容 | 仅应用可见时轮询 |
| 可靠后台提醒 | 不支持 | 首期不支持 | 需要原生通知/调度能力 |
| 白噪音前台播放 | 保持 | 需真机验证 | 受 Android WebView 内核影响 |
| 锁屏持续播放与系统媒体控制 | 尽力支持 | 首期不承诺 | 需要前台媒体服务才可靠 |
| H5 在线更新 | 重新加载后生效 | 重新加载后生效 | 无需重装 APK |
| 原生权限、SDK、桥接新指令 | 不适用 | 需升级 APK | 无法仅通过 H5 发布增加 |

## 4. 更新机制选型

### 4.1 三类更新的边界

| 更新类型 | 适用内容 | 客户端动作 | 是否需要重装/覆盖 APK |
| --- | --- | --- | --- |
| H5 在线发布 | Vue 页面、JS、CSS、文案、已有 API 调用、已有桥接能力的组合 | 重新加载 WebView | 否 |
| WGT 资源包 | 本地 `app-plus` 前端资源，且不增加原生模块/API | 检查、下载、校验、安装并重启 | 否，但本方案首期不需要 |
| APK 整包更新 | 原生权限、SDK、插件、包名、壳层逻辑、新桥接能力 | 应用商店或安装包覆盖安装 | 是 |

### 4.2 本项目的默认选择

- 业务 UI 和业务 JS：通过 H5 在线发布。
- Spring Boot API：通过现有后端发布链路更新，必须保持对旧 H5 会话的向后兼容。
- Android 壳层：只在原生能力或安全边界变化时发布 APK。
- WGT：首期不接入。薄壳本地前端资源很少，引入 WGT 会额外增加版本中心、包校验、最低原生版本和失败回滚成本。

## 5. 目标目录与模块设计

### 5.1 建议目录

```text
<project-root>/
├── budlog-app/                    # 现有 H5，继续是业务 UI 唯一事实来源
├── budlog-android-shell/          # 新增的独立 Android 薄壳
│   ├── package.json
│   └── src/
│       ├── App.vue
│       ├── main.ts
│       ├── manifest.json
│       ├── pages.json
│       ├── config/
│       │   └── environment.ts
│       └── pages/shell/index.vue
├── budlog-server/
└── deploy/
```

薄壳独立建项，不与 `budlog-app` 共用 `pages.json` 和 App Manifest。这样可以避免为了编译一个壳层页面，迫使现有 Naive UI、PWA、DOM 和音频页面全部通过 `app-plus` 编译。

### 5.2 Android 壳层职责

- 根据构建环境加载固定的 Dev/Prod H5 HTTPS URL。
- 显示启动、加载、断网和无法访问服务器状态。
- 正确处理 Android 系统返回键：先回退 WebView 历史，无历史时再退出应用。
- 拦截导航，仅允许预置的 Budlog HTTPS 域名；外部 HTTPS 链接经明确确认后交给系统浏览器。
- 拒绝非 HTTPS、非预期证书错误、`file:`、`content:` 及未白名单自定义 scheme。
- 不把家庭密码、请求头、Cookie 或业务数据记入壳层日志。
- 发布版关闭 WebView 调试，不忽略 TLS/SSL 错误。
- 远程页面默认禁止直接使用完整 `plus` 原生 API。优先按官方隔离方式使用 `plusrequire: "none"` 创建远程子 WebView；如后续需要消息桥接，单独验证受控通信，不为此重新开放完整 `plus` 对象。

### 5.3 H5 内嵌环境职责

- 通过非敏感启动参数和能力握手识别 Android 内嵌环境，例如 `client=android-app`、`shellVersion` 和 `bridgeVersion`。
- 内嵌环境隐藏 PWA 安装入口，默认不注册 PWA Service Worker，避免 App 壳与 PWA 同时管理页面版本。
- 保留普通浏览器环境的 PWA 逻辑不变。
- 在后续引入原生桥接前，所有核心业务仍可以作为普通 H5 完成。
- 使用平台安全区边距，确保顶部和底部固定元素不被状态栏、导航区或手势区遮挡。

## 6. 文件级改造点

| 范围 | 拟涉及文件 | 改造内容 |
| --- | --- | --- |
| H5 运行环境 | `budlog-app/src/utils/runtime.ts` 新增 | 统一检测浏览器、PWA 和 Android 内嵌环境，解析非敏感壳层版本信息 |
| PWA | `budlog-app/src/utils/pwa.ts` | 内嵌环境不注册 Service Worker，不接收 PWA 安装事件 |
| 设置页 | `budlog-app/src/pages/settings/index.vue` | App 内隐藏“桌面应用/添加到主屏幕”入口，可展示 App 版本和 H5 版本 |
| H5 版本 | `budlog-app/src/utils/release.ts` 新增 | 读取发布清单，检测新 H5，发出可延后的刷新提示 |
| 应用生命周期 | `budlog-app/src/App.vue` | 只在合适时机检查新 H5；不在表单编辑中强制刷新 |
| 构建版本 | `budlog-app/vite.config.ts` 及相关构建环境 | 向 H5 注入 `buildId`、构建时间和可选的 Git 提交标识，不注入密钥或连接信息 |
| 发布清单 | H5 构建过程生成 `version.json` | 包含 `buildId`、发布时间、最低壳层版本等非敏感信息 |
| Nginx 缓存 | `deploy/nginx.conf` | `index.html`、`version.json`、`sw.js` 使用 `no-cache`；带哈希资源使用长缓存 |
| H5 发布 | `deploy/build.sh` 或新增的 H5 专用发布脚本 | 先复制新哈希资源，最后原子替换 `index.html` 和版本清单，保留上一版资源供回滚 |
| Android 薄壳 | `budlog-android-shell/` 新建 | 最小 uni-app App 项目、WebView 页、环境 URL、断网/错误状态和返回键处理 |
| App Manifest | `budlog-android-shell/src/manifest.json` | 配置 DCloud AppID、包名、版本、签名和最小权限集，不复制现有过宽权限 |
| Git 忽略 | `.gitignore` | 若新壳层产生 `node_modules/`、`dist/` 或 `unpackage/`，需新增忽略规则；该文件为点文件，后续提交前必须另行人工确认 |

文件名是建议方案，实施时先根据当前 uni-app CLI 生成结构确认，不为追求目录完全一致而大范围搬迁现有 H5。

## 7. 分阶段实施步骤

### 阶段 0：发行前置决策

1. 确定 Dev/Prod H5 的固定 HTTPS URL，证书必须被目标 Android 设备信任。
2. 确定 Android 包名，建议与项目命名保持一致，例如 `dev.oumuv.budlog`。
3. 申请并固定 DCloud AppID，确定 HBuilderX/本地打包路线。
4. 创建 Android 签名密钥并建立离线备份；密钥、口令和证书不写入 Git、项目文档或 CI 日志。
5. 确定发行方式：家庭内部侧载或应用商店。如需上架，再单独核对当期商店对纯 WebView 应用和远程内容更新的审核政策。
6. 确定最低 Android 版本和实际家庭设备清单，真机验收以该清单为准。

验收：所有标识、URL、签名归属和发行方式均有明确结论，不在代码中写入临时生产配置。

### 阶段 1：Android 薄壳概念验证

1. 新建独立 `budlog-android-shell` 项目，依赖版本与现有 uni-app 主版本保持一致。
2. 实现单一壳层页，加载 Dev H5，不接入任何原生桥接。
3. 仅保留网络访问等必需权限，检查 APK Manifest 中没有相机、账户、通话、读日志、写系统设置等无关权限。
4. 实现加载中、断网、连接超时、服务器不可用和重试状态。
5. 实现 Android 返回键和 WebView 历史栈逻辑。
6. 在至少一台真机上完成登录、首页、新增记录、切换页面、退到后台和重启 App 验证。

验收：Android App 可完成核心 CRUD，密码可在 App 重启后按现有逻辑保留，无 CORS 错误，无多余权限。

### 阶段 2：H5 内嵌模式改造

1. 新增统一运行环境检测，不在页面中分散判断 User-Agent。
2. App 启动 URL 只携带 `client`、`shellVersion`、`bridgeVersion` 等非敏感参数，严禁携带家庭密码或会话信息。
3. 内嵌环境隐藏 PWA 安装项，跳过 Service Worker 注册；普通浏览器行为保持不变。
4. 检查全部页面的安全区、底部导航、弹层、输入法顶起和长文本换行。
5. 在设置页显示 H5 版本和 Android 壳版本，用于定位用户现场。
6. 为所有新增环境分支保留默认 Web 退化逻辑，不因桥接不存在而阻断 H5 业务。

验收：同一份 H5 产物在浏览器和 App 中都可使用，平台差异仅限于已列出的 PWA 和壳层信息。

### 阶段 3：H5 版本发布与回滚

1. 构建时生成唯一 `buildId` 和 `version.json`，不使用浮动的客户端时间作为版本判断依据。
2. Nginx 对 `index.html`、`version.json`、`sw.js` 设置 `Cache-Control: no-cache`；对带哈希资源保持长缓存。
3. 发布时先上传新资源，再切换 `index.html`，最后发布 `version.json`；不使用“先删除旧资源、再复制新资源”的窗口期流程。
4. 保留至少上一个 H5 版本和其哈希资源，确保旧页面会话的延迟加载不会立即 404。
5. H5 检测到新 `buildId` 后显示刷新提示；存在未提交表单时允许延后，不强制替换当前页面。
6. 回滚时同时恢复上一版 `index.html`、`version.json` 和配套资源，不只修改版本号。
7. H5 独立发布不执行数据库 migration，不操作生产数据。

验收：发布新 H5 后，浏览器和 Android App 均能在不更新 APK 的情况下获得新页面；回滚后两端都恢复上一版。

### 阶段 4：壳层安全加固

1. 将允许的 H5 origin 编译进对应 Dev/Prod 构建，不提供可任意输入 URL 的地址栏。
2. 记录导航拒绝原因时只记录非敏感事件类型，对 URL 查询参数做脱敏或不记录。
3. 明确禁用远程页面的任意 `plus` API 访问；不通过 `evalJS` 执行来自服务器数据或用户输入的脚本。
4. 检查 WebView 文件、相机、麦克风、定位、下载和外部 scheme 处理；当前业务不需要时全部关闭。
5. 检查正式 APK 不开启 WebView 远程调试，不信任用户安装的任意 CA 或忽略证书错误。
6. 对密码存储、域名跳转、桥接边界、日志和 APK 权限执行一次安全代码审查，按 P0/P1/P2 记录结果。

验收：应用只能加载指定 HTTPS origin，证书异常时失败关闭，APK 权限与已实现功能一一对应。

### 阶段 5：可选原生能力桥接

仅当需求确认需要可靠后台能力时实施本阶段。

1. 定义版本化消息协议，至少包含 `bridgeVersion`、`requestId`、`type`、`payload` 和可枚举的错误码。
2. 先实现只读握手 `getCapabilities`，H5 必须先查能力再调用，旧 APK 遇到新 H5 时应正常降级。
3. 桥接指令使用明确白名单，对消息类型、字段、长度、取值范围和调用频率做校验。
4. 不提供任意文件读写、任意 URL 打开、任意 shell 命令、任意 Java/Kotlin 方法或任意 JS 执行能力。
5. 提醒能力通过原生通知和 Android 允许的调度机制实现；需要新权限时升级 APK。
6. 白噪音如要达到锁屏持续播放和系统媒体控制验收，使用 Android 前台媒体服务，音频 URL/令牌不写入日志。
7. 桥接变更遵循“先发布兼容的 APK，再发布使用新指令的 H5”，禁止反向发布。

验收：新 H5 在旧 APK 中不崩溃、不卡死主流程；所有原生调用都可被白名单、参数模型和版本协议约束。

### 阶段 6：发行与运维固化

1. Dev 和 Prod 使用不同的 App 构建配置与 H5 URL，正式 APK 不允许在设置页临时切换到 Dev。
2. `versionCode` 严格递增，`versionName` 使用固定规则，同时记录壳层版本与最高桥接版本。
3. 正式签名文件和口令仅保存在受控位置，打包日志不打印路径中的敏感信息。
4. 每次 H5 发布记录 `buildId`、上一版本、回滚入口和所需最低壳层版本。
5. 每次 APK 发布记录新增权限、原生模块、桥接指令和已验证设备。
6. 如后续启用 WGT，必须增加包完整性校验、最低原生版本、安装失败回退和重启策略，不与远程 H5 版本号共用同一含义。

验收：开发、H5 发布、APK 发布和回滚具有不依赖个人记忆的可重复流程。

## 8. H5 与后端契约策略

- H5 发布与 App 重新加载不是同一时刻，后端必须允许旧 H5 在一个明确发布窗口内继续调用。
- API 契约变更采用扩展优先：先增加可选字段/新端点，再发布 H5，最后在确认无旧客户端后移除旧契约。
- 不在同一次发布中直接重命名必填字段、改变枚举语义或删除 H5 仍在调用的端点。
- 如某项 H5 功能依赖新桥接，必须通过 `getCapabilities` 或最低壳层版本判断后展示，不仅判断 User-Agent。
- 静态 `version.json` 不包含密码、数据库地址、后端内网地址、签名指纹私钥或可被用于鉴权的值。

## 9. 验证计划

### 9.1 静态检查与构建

- 执行 `git diff --check`。
- 在 `budlog-app` 执行 `npm run type-check` 和 `npm run build:h5`。
- 在 Android 壳项目执行对应类型检查与 App 资源构建。
- 通过 HBuilderX 自定义基座或本地打包生成可安装 APK；仅生成 App 前端资源不等于 APK 验收完成。
- 检查最终 APK Manifest 中的权限、包名、版本号、调试开关和签名证书。

### 9.2 H5 回归

- 在普通桌面浏览器验收现有主要页面和操作。
- 在 `390x844` 视口验收安全区、底部导航、表单、弹层和横向溢出。
- 确认普通浏览器仍可注册 Service Worker 和显示 PWA 安装入口。
- 确认 App 内不显示 PWA 安装入口，不会因 Service Worker 缓存长期停留在旧 H5。
- 验证首页与 `/api/v1/dashboard` 的 HTTP 状态，且 API 仍经同源路径访问。

### 9.3 Android 真机回归

- 覆盖至少一台最旧家庭设备和一台较新 Android 设备，不仅验收模拟器。
- 首次启动、密码验证、记住密码、完全关闭后重启、清除 App 数据和卸载重装分别验证。
- 逐页验证首页、记录、分析、任务、日历、设置、白噪音和所有编辑页。
- 验证系统返回键、前后台切换、锁屏恢复、系统回收后恢复和输入法弹出/收起。
- 验证断网启动、运行中断网、网络恢复、DNS 失败、服务器 5xx 和超时。
- 验证外部链接、非白名单域名、HTTP URL、非法 scheme 和 TLS 证书错误均按设计处理。
- 白噪音前台播放要实际播放验证；后台和锁屏结果记录为兼容性现象，首期不将尽力支持描述为保证。

### 9.4 H5 在线发布验收

1. Android 设备安装固定 APK，打开 H5 版本 A。
2. 在不更新 APK 的前提下发布 H5 版本 B。
3. 确认当前正在编辑的表单不被自动刷新。
4. 确认用户主动刷新或重新打开 App 后加载版本 B。
5. 确认旧会话在刷新前仍能请求其依赖的哈希资源。
6. 回滚到 H5 版本 A，确认浏览器和 App 重新加载后均恢复 A。
7. 通过网络请求和页面版本展示核对 `index.html`、`version.json` 和资源版本一致。

### 9.5 最终检查

- 执行 Compose 健康检查和首页/Dashboard API HTTP 冒烟。
- 执行安全审查，按 P0/P1/P2 汇报发现与剩余风险。
- 检查 `git status`、`git diff --stat` 和实际 diff，区分本次改造与用户已有变更。
- 不修改 `.env`、已应用 Flyway migration、Maven 本地仓库或生产数据。
- 未经确认不提交、不推送、不发布生产 APK 或 H5。

## 10. 验收标准

1. 现有 H5 URL 和功能保持可用，浏览器端不依赖 Android 壳层。
2. Android APK 通过固定 HTTPS 域名加载同一 H5，核心 CRUD 和鉴权流程可用。
3. H5 从版本 A 发布到 B 后，已安装 APK 无需升级即可在刷新/重开后使用 B。
4. 新 H5 发布不强制刷新未保存表单，旧页面会话的配套资源不立即失效。
5. H5 可独立回滚且不需要回滚 APK；后端契约保证发布窗口内的新旧 H5 兼容。
6. 家庭密码不出现在 URL、壳层日志、版本清单或原生桥接握手中。
7. App 只能加载白名单 HTTPS origin，不忽略 TLS 错误，远程页面没有任意原生调用能力。
8. APK 权限与已交付功能完全对应，没有复制现有 Manifest 中的无关高权限。
9. 能够清晰说明一次改动应当发布 H5、WGT 还是 APK，不把原生能力变更误当成 H5 热发布。
10. 所有完成结论均有构建、HTTP、Android 真机或实际页面截图证据支持。

## 11. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| H5 发布会同时影响浏览器和 App | 单次缺陷影响面更大 | 先 Dev/真机验收，发布保留上一版并支持快速回滚 |
| 旧 WebView 内核差异 | 部分 CSS/Web API 行为不一致 | 以实际家庭设备建立最低兼容基线，不只测最新设备 |
| 更新期间删除旧哈希资源 | 已打开页面的懒加载请求 404 | 新资源先发布，保留至少上一版资源，最后切换入口 |
| 强制刷新中断编辑 | 表单数据丢失 | 仅提示更新，保留延后选项，后续再建立统一脏表单检测 |
| 远程 H5 获得过大原生权限 | Web 供应链问题可放大为本机风险 | 禁用完整 `plus` API，桥接白名单、参数校验、版本化和安全 CR |
| H5 更新依赖新 APK 能力 | 旧 APK 功能失败 | 先发兼容 APK，H5 通过能力握手渐进启用 |
| WebView 后台计时器/音频被限制 | 提醒不及时或音频中断 | 首期明确不承诺；有硬需时改为原生通知与前台媒体服务 |
| WebView 本地存储与浏览器不共享 | 用户首次进入 App 需再登录 | 作为正常产品行为说明，不通过 URL 传递密码解决 |
| 更换 H5 域名 | WebView origin 变化，本地存储与 Cookie 不再复用 | 正式发布前固定域名；域名迁移按独立项目处理 |
| 应用商店审核政策变化 | 纯 WebView 壳可能被要求增加原生价值 | 内部侧载与商店发行分开决策，上架前检索当期官方政策 |
